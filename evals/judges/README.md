# 共享评审者

被测 agent 的工作要从几个固定角度评：写出的 Eval 有没有 NiceEval 品味、文件放得对不对、有没有在评估机上乱留东西、交接是否如实。这些角度的标准与取证纪律对每道题都一样，所以定义成共享的评审者（Agent Judge 或普通 Judge 的 instructions），各题按需调用。

普通 Judge 和 Agent Judge 使用项目 `judgeProvider` 配置的 `gpt-6.2-sol`。

## 分工

- **评审者（本目录）拥有**：身份、要套用的标准全文、取证纪律（只读、只走公开 CLI、不读私有 Record 与实现源码、不输出凭据、不替 agent 补做运行）。标准变化只改这里，调用它的题一起失效。
- **题目拥有**：这道题具体判什么、每条判据多少分、交给评审者的材料与上下文。判据仍平铺在 `eval.ts` 的打分处，读一个 `eval.ts` 就能看出测什么、什么算通过。评审者已经带着标准，所以判据写一句具体命题即可，不复述标准。
- **确定性取证**：能直接读到的事实（改了哪些文件、留下哪些进程与临时文件、调用过哪些工具）由本目录的取证函数确定性收集，作为材料交给评审者；评审者只做需要判断的部分。

## 评审者

| 评审者 | 回答的问题 | 典型使用 |
| --- | --- | --- |
| NiceEval 品味 | 写出的 Eval / Experiment / Adapter 是否符合 NiceEval 品味：判据平铺在打分处、事实用确定性检查、判据写在 Match 上、未知保持未知、Judge 判据写成陈述句、题面与判据不泄题 | 所有 authoring 题、安装题的产出质量 |
| 项目结构 | 新文件放在宿主项目与 NiceEval 约定的位置；目录与命名和既有结构一致；没有把一次性脚本、副本或草稿混进项目；依赖归属在正确的 manifest | 安装题、authoring 题、organize-refund、concord-rsi 的新增实验 |
| 收拾现场 | 交付时评估机上只留交付物：自己启动的后台进程已停，临时测量输出、草稿与副本已删或放在约定位置 | 所有会运行命令的题；依据确定性现场快照 |
| 交接如实 | 交接中的数字、Run / Attempt locator 与公开结果一致；残余失败如实说明；复现命令可执行；局部结果标明范围 | 所有要求交接的题 |
| 提问得当 | 只在缺少会实质影响结果的信息时提问；能从仓库、公开结果或文档查到的不问；问题具体、可直接回答 | 有模拟用户的多轮题 |
| 范围与成本纪律 | 改动没有越出用户授权的范围，没有顺手重构或格式化；付费运行只跑必要范围，没有为变绿反复重跑 | 有明确授权边界或付费运行的题 |

每个评审者的标准全文写在它的模块里，并注明来源（NiceEval 品味来自 NiceEval 仓库 `docs/taste.md` 的相应条目），不在本页复述。

## 评审者怎么写

每个评审者都是一个完整的 Agent Judge，有自己的身份与标准；不定义没有身份的通用评审者。Agent Judge 在 Sandbox 里能执行只读命令，所以评审者不只看材料：题目交给它的确定性材料（例如现场快照、提问清单）固定了“看哪些东西”，评审者再进 Sandbox 逐项查证。外层验收在被测会话之后运行，它产生的文件与进程不属于被测 agent，评审者以材料的时点为准。共享的取证纪律只写一份，由各评审者拼接。

instructions 按同一结构写，宁可详细，也不要让 Judge 凭自己的理解补标准：

1. **身份与立场**：你是谁、评什么；对被测 agent 的说法默认存疑，以可核实的证据为准。
2. **标准**：只列本评审者负责的条目。每条写清是什么、为什么重要，并各给一个通过与不通过的例子；来自 NiceEval `docs/taste.md` 的条目注明编号。
3. **取证方法**：按下表写清要看什么、用什么只读命令看；区分确定性材料、可在 Sandbox 核实的事实与 agent 的自述。
4. **判定规则**：什么情况算满足命题；常见边界情况怎么判；二元判据没有部分得分；证据不足时判不满足并说明缺口。
5. **输出要求**：结论附可复查的证据（文件与行号、命令及输出摘录、Run / Attempt locator），并写明未能核实的部分。
6. **共享取证纪律**。

### 各评审者看什么、怎么看

| 评审者 | 要看什么 | 怎么看（只读） |
| --- | --- | --- |
| NiceEval 品味 | agent 新写或改动的 Eval、Experiment、Adapter 全文；它们实际产生的计划与结果 | `git diff --stat` 与 `git diff` 对照基线；完整读改动文件，不只看片段；`niceeval exp <实验> --dry` 看计划与身份诊断；`niceeval show <locator> assertions --json` 看判据实际怎么登记和判定 |
| 项目结构 | 新文件与依赖落在哪里，是否沿用宿主既有约定 | `git status --porcelain`、`git diff --stat`；`ls` 既有 `evals/`、`experiments/`、`agents/` 等目录对照命名与层级；读 `package.json`、锁文件 diff 与 `niceeval.config.ts`；确认交付物能从项目正常入口发现（`niceeval list`） |
| 收拾现场 | 现场快照列出的残留进程、临时文件、项目内交付范围外的新文件 | 从快照出发：`ps -o pid,etime,user,args -p <pid>` 确认进程仍在及其命令；`ls -la`、`du -sh`、`head` 查看残留文件内容，判断是测量输出、草稿、副本还是交付物；快照之后才出现的东西不计 |
| 交接如实 | 交接里的每个数字、locator、结论与复现命令 | `niceeval show run:<id> --json`、`niceeval show @<attempt> assertions`、`query run.list` 核对数字与样本范围；复现命令用 `--dry` 验证能解析到所述范围，不真实运行 |
| 提问得当 | agent 提出的每个问题，以及答案是否本可自行查到 | 题目提供的提问清单；用 `rg`、读 `node_modules/niceeval/INDEX.md` 与随包文档、读仓库文件，核对答案是否本可查到；对照题面判断问题是否影响结果 |
| 范围与成本纪律 | 改动范围与真实运行的次数、范围 | `git diff --stat` 对照授权范围；`niceeval show runs --json` 与各 Run 的成员数核对运行了哪些格、多少次、是否有 `--rerun all` 或重复跑同一条件 |

## 效率记录

被测会话的轮数、工具调用次数、token 用量与墙钟时长由取证函数从公开 Turn 与用量结果确定性读出，写进 `t.note` 供跨候选横向比较，不计分：不同题目的合理用量差异很大，先积累分布再决定是否设阈值。

## 现场快照

“收拾现场”依赖一份确定性快照：题目在第一次 `t.send` 前取时间标记，在被测会话结束后、任何外层验收运行之前采集：

- 会话开始后启动且仍存活的进程（排除 NiceEval runner、被测 agent 自身与外层进程）；
- `/tmp` 与 agent 家目录下比标记新、仍存在的文件与目录及大小，数量有上限并标明截断；
- 项目内超出该题交付范围的新文件，交付范围由题目声明。

外层自己的测量产物不计入。快照同时写进 `t.note`，便于复查。

## 采用与身份

评审者模块被哪些题导入，就只影响那些题的身份。把一道题改用共享评审者属于判据变化，下次运行该题会重跑；按工作区成本纪律，批量采用前先确认重跑范围与成本。
